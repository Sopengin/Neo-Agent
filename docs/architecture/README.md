## 项目一句话

**Neo Agent** 是一个 **企业级 AI 智能体对话平台**，覆盖智能对话、文档知识问答、联网搜索、RAG 检索、MCP 工具协议、Skills 能力扩展、会话记忆管理、文档全生命周期治理。

**核心设计哲学：**

> **「确定性编排 + 场景化执行」**
> 不是让 Agent 自己决定所有事情，而是先用确定性的编排逻辑做好决策，再把执行交给最合适的引擎。
> 能确定的事情先确定好，只把真正需要自主探索的部分交给 Agent。

## 核心链路一图流

```
用户提问
   ↓
① 会话记忆加载     ConversationMemoryService        （无记忆 / 滑动窗口 / 摘要压缩）
   ↓
② 前置编排决策     ChatPreparationOrchestrator      （五步决策链）
   │   路由判定 → 问题改写 → 歧义检测 → 子问题拆分 → 知识域收缩
   │   产出：ConversationExecutionPlan
   ↓
③ 执行器分发       ConversationExecutorRegistry     （按 ExecutionMode 选执行器）
   │   优先级：歧义澄清 > 知识问答 > 开放式 Agent
   ↓
④ 回答生成         各 Executor
   │   RAG 知识问答 / 图结构导航 / ReAct Agent
   ↓
⑤ SSE 流式输出     StreamEventWriter
   │   正文分片 → 引用来源 → 推荐追问
   ↓
⑥ 会话记忆更新     持久化 + 摘要压缩（如需）
```

**每一步的输入输出、耗时、决策结果都有完整 Trace 记录。**

### 五种执行器（判断顺序：歧义澄清 > 知识问答 > 开放式 Agent）

| 执行器 | 触发条件 | 处理方式 |
|-------|---------|---------|
| `ClarificationExecutor` | 信息量不足，无法确定意图 | 生成澄清问题，引导用户补充 |
| `RagChatExecutor` | 问题可在知识库找到答案 | 证据驱动生成，引用可追溯 |
| `ReactAgentExecutor` | 需联网搜索 / 多步推理 | 自主决策 + 工具调用 + 多轮推理 |
| `GraphOnlyExecutor` | 纯结构定位类问题 | 只走 Neo4j 图查询 |
| `GraphThenEvidenceExecutor` | 结构定位 + 内容补充 | 先定位章节，再读具体内容 |

> **为什么不是所有问题都走 Agent？** 知识问答追求「稳」和「可解释」。让 Agent 自由探索容易不可控（可能跑去联网搜一堆无关内容）。
> **在企业级系统中，可控比聪明更重要。**

## 关键参数速查

### 1. Agent 安全限制（防止死循环 / 资源滥用）

| 机制 | 参数 | 值 |
|------|------|-----|
| 单次模型调用上限 | `ModelCallLimitHook` | **8 次** |
| 单次工具调用上限 | `ToolCallLimitHook` | **6 次** |
| 会话模型调用累计上限 | 每线程 | **40 次** |
| 会话工具调用累计上限 | 每线程 | **30 次** |
| 工具重试 | `ToolRetryInterceptor` | 最多 **2 次**，指数退避 200ms→1200ms，带随机抖动 |
| 工具异常兜底 | `ToolErrorInterceptor` | 优雅降级，不抛给用户 |
| 并行工具执行 | `parallelToolExecution` | 最多 **4 个**并行 |

### 2. 检索与证据预算

| 参数 | 默认值 | 说明 |
|------|-------|------|
| 单子问题证据上限 | **2200 字符** | 防止单个子问题证据过多 |
| 全部证据总预算 | **5200 字符** | 控制注入 Prompt 的总证据量 |
| 单父块最大字符 | **2200 字符** | 防止单个父块占用过多预算 |
| 向量检索最低相似度 | **0.45** | 绝对阈值，过滤低质量向量匹配 |
| 关键词检索相对阈值 | **0.35** | 相对 topScore 裁剪弱命中 |
| 单轮子问题拆分上限 | **4 个** | 避免过度切碎 |
| 通道超时 / 子问题超时 | **5s / 12s** | 失败自动降级 |

### 3. RRF 融合

```
score = Σ 1 / (k + rank_i)      k = 60
```

**为什么用 RRF？** 向量检索和关键词检索的**分数量纲完全不同，不能直接比大小**。
RRF 只依赖**排名**、不依赖绝对分数，因此可以直接融合异构检索结果。
一个文档若在两路中排名都靠前，融合分数就高。

### 4. 会话记忆（摘要压缩策略）

| 参数 | 值 |
|------|-----|
| 最近原文保留轮数 | **4 轮**（不做压缩） |
| 单次摘要推进上限 | **6 轮**（避免一次处理超长历史） |
| 最近原文窗口最大 | **2200 字符** |
| 长期摘要最大 | **1400 字符** |
| 持久化位置 | MySQL（应用重启不丢失） |

> **增量摘要的意义**：每次都只处理新增的几轮，融合进已有摘要。
> 这样不管对话多长，**每次摘要的成本都是固定的**（而非线性增长）。

### 5. 集群并发控制

| 机制 | 参数 |
|------|------|
| Redis 租约 TTL | **30 秒** |
| 租约续期间隔 | **10 秒** |
| 锁键格式 | `chat:running:{conversationId}` |

### 6. 知识路由

| 参数 | 值 |
|------|-----|
| 一级 Scope 候选数 | Top **5** |
| 二级 Topic 候选数 | Top **8** |
| Scope 归属加分（Topic 级） | **+8** |
| Scope 匹配加分（Document 级） | **+15** |
| Topic 关联加分（Document 级） | **×20** |
| 置信度公式 | `topScore / max(10, topScore + secondScore + 5)` |
| 置信度阈值 | **≥ 0.55 → SUCCESS**；0 < x < 0.55 → LOW_CONFIDENCE；无候选 → FAILED |
