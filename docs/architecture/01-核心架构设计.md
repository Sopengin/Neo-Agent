# 02 - 核心架构设计

---

## 1. 完整请求链路

一条用户消息从进入系统到返回回答，经过 **6 个阶段**：

| # | 阶段 | 做什么 |
|---|------|-------|
| 1 | **会话记忆加载** | 从 MySQL 加载历史记忆，按配置策略（无记忆/滑动窗口/摘要压缩）组装上下文 |
| 2 | **前置编排决策** | LLM 分析意图，执行 **五步决策**：路由判定 → 问题改写 → 歧义检测 → 子问题拆分 → 知识域收缩 |
| 3 | **执行器分发** | 按编排结果选执行器：歧义追问 / RAG 知识问答 / ReAct Agent |
| 4 | **回答生成** | 执行器执行检索或推理，生成最终回答 |
| 5 | **SSE 流式输出** | 正文分片推送 + 引用来源补发 + 推荐追问生成 |
| 6 | **会话记忆更新** | 持久化本轮对话，触发摘要压缩（如需） |

**每一步的输入输出、耗时、决策结果都有完整 Trace 记录，出问题可精确定位。**

### 核心设计哲学

> **「确定性编排 + 场景化执行」**

大多数项目把所有问题扔给一个 Agent，结果是**不可控、不可解释**。
本项目的做法：**能确定的事情先确定好，只把真正需要自主探索的部分交给 Agent。**

## 2. Agent 设计中的关键决策

| 设计问题 | 处理方式 |
|------|------|
| **系统怎么决定用哪种方式回答？** | 不是让模型自己选，而是先经**路由判定 → 问题改写 → 歧义检测**整轮编排。判断顺序：**歧义澄清 > 知识问答 > 开放式 Agent** |
| **为什么不是所有问题都走 Agent？** | 知识问答追求「稳」和「可解释」，让 Agent 探索容易不可控。只有需联网搜索、多步推理的**开放式问题**才走 Agent |
| **Agent 死循环怎么办？** | `ModelCallLimitHook` 限制单次最多调模型 **8 次**；`ToolCallLimitHook` 限制 Tavily 最多调 **6 次**。会话线程累计上限分别 **40 次 / 30 次** |
| **联网搜索失败怎么处理？** | `ToolRetryInterceptor` 指数退避重试（最多 2 次，初始 200ms，最大 1200ms，带随机抖动）；最终失败由 `ToolErrorInterceptor` 兜底，不抛异常给用户 |
| **对话状态怎么持久化？** | 用 Spring AI Alibaba 的 `MysqlSaver` 把 ReactAgent 的 Checkpoint 存到 MySQL，**应用重启后可继续之前的对话** |
| **并行工具执行怎么做？** | ReactAgent 配置 `parallelToolExecution`，最多 **4 个**工具并行 |

## 3. 三层执行器

### 为什么分层

- **知识问答**追求「稳」「可解释」：用户问「退款规则是什么」，需要从文档精准检索证据，再让模型基于证据生成。让 Agent 自己探索反而可能跑去联网搜一堆无关内容。
- **开放式问题**（如「今天北京天气怎么样」）知识库没有答案，必须让 Agent 调用搜索工具获取实时信息。

### 执行器表

| 执行器 | 触发条件 | 处理方式 |
|-------|---------|---------|
| 歧义追问执行器 | 问题信息量不足，无法确定意图 | 生成澄清问题，引导补充信息 |
| RAG 知识问答执行器 | 问题可在知识库找到答案 | 证据驱动生成，引用来源可追溯 |
| ReAct Agent 执行器 | 需联网搜索、多步推理的开放式问题 | 自主决策 + 工具调用 + 多轮推理循环 |

### 优先级链的理由

```
歧义澄清  >  知识问答  >  开放式 Agent
```

- **歧义优先**：信息不足时任何回答都可能是错的，不如先问清楚。
- **知识问答优先于 Agent**：知识库回答**可控、可解释、可追溯来源**；Agent 自由探索能力更强但**不可预测性更高**。

> **在企业级系统中，可控比聪明更重要。**

## 4. Agent 安全机制

在生产环境中，Agent 的自主决策能力是**双刃剑**——可能陷入无限推理循环、过度消耗搜索资源，甚至因工具调用异常导致会话崩溃。

| 安全机制 | 配置参数 | 作用 |
|---------|---------|------|
| 单次模型调用上限 | `ModelCallLimitHook` = **8 次** | 防止单次请求陷入死循环 |
| 单次工具调用上限 | `ToolCallLimitHook` = **6 次** | 防止搜索工具被过度调用 |
| 会话模型调用累计上限 | **40 次 / 线程** | 防止长对话累积消耗过多资源 |
| 会话工具调用累计上限 | **30 次 / 线程** | 控制整体工具使用成本 |
| 工具重试机制 | 最多 **2 次**，指数退避 200-1200ms | 容忍短暂网络抖动 |
| 异常兜底 | `ToolErrorInterceptor` | 工具彻底失败时优雅降级，不影响主流程 |

> 观测面板的轮次详情中可看到：输入/输出/总 Token、费用估算、模型调用次数和工具调用次数相对于上限的使用进度。

## 5. 前置编排器：五步决策链

系统不会把所有问题直接扔给模型，而是先做一轮完整编排。

### 5.1 路由判定

判断消息属于哪种类型：
- 可在知识库找到答案？
- 需联网搜索的开放式问题？
- 信息不全需先追问？

> **本质是一次带结构化输出的 LLM 调用**。系统把「用户当前问题 + 最近几轮历史 + 知识库元信息」一起传给模型，让模型判断最适合走哪个执行器。
> 比基于规则的路由**更灵活**，能处理各种模糊边界情况。

### 5.2 问题改写

用户问题往往不适合直接检索，需补全省略信息。

| 原始问题 | 改写后 | 改写原因 |
|---------|-------|---------|
| 那它怎么配置？ | MinIO 对象存储怎么配置？ | 指代消解，补全主语 |
| 还有其他方案吗？ | 除了向量检索，还有其他检索方案吗？ | 补全省略的上下文 |
| 怎么用？ | Spring AI 的 ChatClient 怎么使用？ | 结合前文话题补全完整问题 |

### 5.3 子问题拆分

复合问题（如「退款规则是什么？审批流程怎么走？」）直接检索会让两个意图互相干扰。

**拆成独立子问题，每个单独走检索链路，最后合并结果。单轮最多拆 4 个子问题**，避免过度切碎。

### 5.4 意图解析与知识域收缩

分析每个子问题属于哪个**知识域**，把检索范围从「全库」缩小到「相关领域」。

> **示例**：知识库含「产品手册」「开发文档」「HR 制度」三个领域。用户问「年假怎么申请」，全库检索可能因产品手册也含「申请」而引入噪声。知识域收缩会先判断这是 HR 问题，**只在「HR 制度」领域内检索**，大幅提升精准度。

### 5.5 歧义检测

问题信息量不够（如「查一下那个」）时，**不硬着头皮检索**，而是生成澄清问题让用户补充。这比返回不相关答案体验好得多。

## 6. 编排器的产出物：ConversationExecutionPlan

前置编排的最终产物是结构化执行计划，是**编排层与执行层之间的标准契约**：

| 字段 | 说明 | 示例 |
|------|------|------|
| `executionMode` | 执行模式 | `CLARIFY` / `RAG_CHAT` / `REACT_AGENT` |
| `rewrittenQuestion` | 改写后的完整问题 | "MinIO 对象存储怎么配置连接参数？" |
| `subQuestions` | 拆分后的子问题列表 | `["退款规则是什么", "审批流程怎么走"]` |
| `knowledgeDomains` | 知识域范围 | `["产品手册", "运维文档"]` |
| `clarifyQuestion` | 澄清问题（仅 CLARIFY 模式） | "请问你想了解的是哪个产品的配置？" |

> 执行器只需根据计划执行，**不需要关心编排过程的细节**。这种解耦使编排逻辑和执行逻辑可以**独立演进**。

## 7. 检索链路细节

### 7.1 问题进来之后

- 「那它怎么配置？」这类省略主语的追问，直接检索什么都找不到 → **必须先问题改写**，结合最近几轮历史补全指代
- 一个问题问两件事 → **拆成独立子问题**，各自走检索链路
- 单轮最多拆 **4 个**子问题

### 7.2 检索是怎么做的（双通道并行）

- **不是只用向量检索**。用户问订单号、配置项名，向量检索很可能找不到 → 用**双通道并行：向量检索 + 关键词检索**，两路同时出发，互不阻塞
- 两路结果**分数量纲完全不同，不能直接比大小** → 用 **RRF（Reciprocal Rank Fusion）** 按排名倒数法融合
- **向量通道**设最低相似度；**关键词通道**用相对阈值；低于阈值的弱命中直接过滤
- 融合后可接**外部 Rerank 精排**（支持 SiliconFlow 兼容协议），在较干净的候选集上继续优化排序
- 检索粒度用 **Child 小块**保证命中率，回答阶段通过 **Parent-Child 聚合**提升到 **Parent 大块**保证上下文完整性

### 7.3 RRF 融合原理

```
score = Σ 1 / (k + rank_i)
```
- `k`：常数，通常为 **60**
- `rank_i`：文档在第 i 路检索结果中的排名

> **巧妙之处**：不依赖原始分数绝对值，**只依赖排名**，因此可以直接融合不同量纲的检索结果。
> 一个文档如果在**两路检索中排名都靠前**，融合后的分数就会很高。

### 7.4 父子块聚合

这是检索链路中最精巧的设计之一：

```
检索阶段：用 Child 小块   → 小块语义集中，更容易被向量检索命中（保精度）
回答阶段：聚合到 Parent 大块 → 保证回答时有足够上下文（保完整性）
```

> **检索用小块保精度，回答用大块保完整性。** 业界比较前沿的实践。

### 7.5 证据够不够怎么判断

- **无证据短路**：最终没有任何有效证据时，**直接短路返回**，告诉用户「当前文档中没有检索到足够证据」。**不让模型凭空编造**——这是防幻觉最直接的手段
- **证据预算控制**：证据太多时按「单个子问题字符 / 全部证据总预算 / 单个父块最大字符」裁剪，防止把模型上下文窗口吃满

### 7.6 最终怎么组装回答

1. 按**子问题边界**分别组织证据，注入 Prompt，模型按编号逐一回答
2. 要求模型在引用证据时**标注来源编号 `[1][2]`**
3. 答案通过 **SSE 实时流式推送**，结束时补发**引用来源**和**推荐追问问题**

### 7.7 证据预算控制参数

| 参数 | 默认值 | 说明 |
|------|-------|------|
| 单子问题证据上限 | **2200 字符** | 防止单个子问题的证据过多 |
| 全部证据总预算 | **5200 字符** | 控制注入 Prompt 的总证据量 |
| 单父块最大字符 | **2200 字符** | 防止单个父块占用过多预算 |
| 向量检索最低相似度 | **0.45** | 过滤低质量向量匹配 |
| 关键词检索相对阈值 | **0.35** | 过滤弱命中的关键词结果 |

## 8. 文档从上传到可检索

> 不是「切成固定长度 → 向量化 → 完事」。不同文档差异很大，一刀切效果很难好。

完整异步流水线：**上传存储 → 异步解析 → 策略推荐 → 组合切块 → 向量化 → 双引擎索引**

| 步骤 | 内容 |
|------|------|
| **① 上传和存储** | 文件上传 MinIO → Kafka 异步触发解析任务；Apache Tika 处理 PDF/Word/PPT（表格、扫描件、双栏排版都是坑）；可配置知识域编码/名称、业务分类、文档标签等元信息 |
| **② 异步解析和策略推荐** | 解析后**自动推荐最优切块策略组合**（不是让用户盲选）；用户可查看推荐结果或手动调整（如低质量文档额外开启 LLM 智能切块） |
| **③ 组合式切块引擎** | 四种策略各司其职的**组合流水线**（见下表） |
| **④ 向量化与双引擎索引** | Kafka 异步执行；向量写向量库，关键词写倒排索引；**每步有独立任务日志，可精确定位失败点** |

### 四种切块策略

| 策略 | 角色 | 什么时候用 |
|------|------|-----------|
| 基于文档结构切块 | **主干** | 按标题/章节/段落切成语义完整的块 |
| 递归分块 | **兜底** | 结构块太大时继续往下裁剪，控制块大小 |
| 语义分块 | **优化** | 在结构切块基础上做边界精修 |
| LLM 智能切块 | **增强** | 处理低质量文档和复杂文档，**默认关闭** |

> 一句话：**结构负责保留文档天然边界，递归负责控制块大小，语义负责优化块边界，大模型负责处理疑难场景。**

**推荐示例**：
- 含标题层级的产品手册 → 结构切块（主干）+ 递归分块（兜底）
- 段落很长且话题跳跃频繁 → 额外开启语义分块优化边界
- 扫描后 OCR 识别的低质量文档 → 手动开启 LLM 智能切块

## 9. 会话记忆：Token 成本 vs 上下文完整性

### 三种策略

| 策略 | Token 成本 | 上下文完整性 | 适用场景 |
|------|-----------|-------------|---------|
| **无记忆** | 最低 | 无 | 一次性查询、FAQ 问答 |
| **滑动窗口** | 中等 | 最近 N 轮完整 | 短期连续追问、调试场景 |
| **摘要压缩** | 可控 | 长期摘要 + 近期原文 | **生产环境长对话（最推荐）** |

### 摘要压缩的具体设计

| 参数 | 值 |
|------|-----|
| 最近原文保留轮数 | **4 轮**（不做压缩） |
| 单次摘要推进上限 | **6 轮**（避免一次处理超长历史） |
| 最近原文窗口最大 | **2200 字符** |
| 长期摘要最大 | **1400 字符** |
| 持久化 | MySQL，应用重启不丢失 |

> **为什么要增量摘要？**
> 如果每次都对全部历史做摘要，对话越长摘要输入越大，**成本和延迟线性增长**。
> 增量摘要每次只处理新增的几轮，融合进已有摘要——**不管对话多长，每次摘要成本都是固定的**。

## 10. MCP 工具协议与 Skills 能力扩展

### 10.1 MCP（Model Context Protocol）

Anthropic 提出的开放协议标准，定义模型与外部工具的通信规范。

| 能力 | 说明 |
|------|------|
| **动态工具发现** | Agent 启动时自动扫描并注册可用工具，不需要硬编码工具列表 |
| **标准化通信** | 输入输出遵循 MCP 规范，支持 **Stdio 和 SSE** 两种传输模式，兼容主流 MCP Server 生态 |
| **参数自动提取** | 模型根据用户意图自动识别工具并提取参数 |
| **多工具编排** | 单次对话可串联调用多个工具，前一个的输出可作为后一个的输入 |
| **安全沙箱** | 受控环境执行，有超时限制和异常隔离 |

> 相比传统 Function Call 硬编码，MCP 的优势是**标准化和可扩展性**——新增工具不需要改任何业务代码，只需部署一个符合 MCP 协议的 Server。

### 10.2 Skills

比 MCP 更上层的能力抽象，解决「Agent 怎么获得特定领域的专业能力」。

| 特性 | 说明 |
|------|------|
| **声明式定义** | 每个 Skill 通过 `SKILL.md` 描述能力边界、触发条件、执行逻辑 |
| **目录化管理** | 按领域组织成目录，支持嵌套分类 |
| **自动加载** | 启动时自动扫描目录，新增即生效，**零配置** |
| **引用脚本与资料** | 可关联外部脚本（Python/Shell）和参考文档，执行时自动加载上下文 |
| **能力组合** | 多个 Skills 可组合使用 |

### 10.3 MCP 与 Skills 的关系

```
MCP    解决「工具怎么调」  → 标准化工具的通信协议
Skills 解决「能力怎么扩」  → 让 Agent 获得领域知识和决策框架

两者互补：MCP 提供工具执行能力，Skills 提供领域知识和决策框架。
一个 Skill 可以调用多个 MCP 工具来完成复杂任务。
```

## 11. 全链路可观测

基于 **AOP** 做全链路追踪，每轮对话的完整执行过程都能在观测面板看到。

**执行阶段时间线示例**：
```
会话记忆加载 → 问题改写 → 路由判定 → 结构图查询 → 推荐问题生成 → 收尾归档
```
> 每个阶段耗时、关键决策结果一目了然。

**价值**：用户反馈「回答不准确」或「响应太慢」时，传统做法是翻日志、加断点、猜测。
有了全链路追踪，直接打开观测面板就能看到：编排器走了哪个分支、检索了哪些文档、证据评分多少、模型用了多少 Token。**问题根因一目了然。**
