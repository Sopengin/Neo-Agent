# 04 - 图数据库与知识路由

---

## 0. 要解决的核心问题

> **用户提了一个问题，系统怎么知道应该去哪份文档里找答案？**

文档只有两三份时不是问题。但当文档上了几十上百份，**每次都全库检索不仅慢，而且噪声很大**。

**典型问题——跨域干扰**：
```
用户问：「年假怎么申请」
全库检索 → 从产品手册里也检索出包含「申请」这个词的段落  ❌
```

### 两个解决手段

1. **Neo4j 图数据库**：把每份文档的内部结构（章节、段落、条目）建成一张图，让系统能**沿着文档结构精准导航**，而不是只靠向量匹配碰运气
2. **知识路由三级漏斗**：进入检索链路之前，先通过 **Scope → Topic → Document** 三级排序，自动锁定最相关的文档
3. **影子路由**（附加设计）：持续观测路由质量

---

## 1. 为什么需要图数据库

### 1.1 向量检索和关键词检索都处理不了的问题

| 用户问题 | 问题类型 | 为什么传统检索不行 |
|---------|---------|------------------|
| 「第三章第二节讲了什么？」 | **结构定位** | 「第三章第二节」不是语义概念也不是关键词，需要知道文档目录结构 |
| 「上一节讲的是什么？」 | **邻接查询** | 需要知道当前节点的前一个兄弟节点是谁 |

> 用关系型数据库也能做，但会**非常别扭**——得写一堆递归查询来遍历树结构。
> 图数据库天生就是干这个的，**节点和关系就是它的一等公民**。

### 1.2 为什么选 Neo4j

- 图数据库领域的**事实标准**
- **Cypher 查询语言**对图遍历的表达力远超 SQL
- 文档结构天然就是一棵树（Document → Section → Item），用图存储和查询最自然
- Java Driver 与 Spring 生态集成好，接入成本低

## 2. Neo4j 中的文档结构图谱

每份文档完成索引构建后，系统会**同步在 Neo4j 中生成一张结构图谱**。

### 2.1 三种节点类型

| 节点类型 | 说明 | 关键属性 |
|---------|------|---------|
| **Document** | 文档根节点，一份文档对应一个 | `documentId`、`title` |
| **Section** | 章节节点，对应文档中的标题层级 | `nodeCode`（如 `"1.2.3"`）、`title`、`normalizedPath`、`canonicalPath`、`contentText` |
| **Item** | 条目节点，对应步骤、列表项等细粒度内容 | `anchorText`、`contentText` |

### 2.2 支持的图查询能力

| 能力 | 说明 | 依赖 |
|------|------|------|
| **章节编号定位** | 用户问「1.2.3 节讲了什么」，直接精准定位 | `nodeCode` |
| **标题路径查找** | 用户提到「考勤制度下面的请假流程」 | `normalizedPath` |
| **邻接遍历** | 用户问「上一节 / 下一节是什么」 | `NEXT_SIBLING` 关系 |
| **子节点展开** | 用户问「这一章有哪些内容」 | `HAS_CHILD` 关系 |
| **最佳匹配** | 给定主题和关键词，找语义最接近的章节 | - |

### 2.3 图查询 vs 向量检索的分工

```
图查询擅长的  → 结构性问题（「第几章」「上一节」「目录」）
向量检索擅长的 → 语义性问题（「怎么请假」「墨盒怎么换」）
```

> **`DocumentQuestionRouter` 会先分析问题类型**：
> - 结构性问题 → 走图查询（`GRAPH_ONLY` 或 `GRAPH_THEN_EVIDENCE` 模式）
> - 语义性问题 → 走混合检索（`RETRIEVAL` 模式）
>
> **两条路径各司其职，不是非此即彼。**

## 3. 知识路由：三级漏斗自动选文档

### 3.1 类比

> 你去图书馆找资料，不会把所有书架翻一遍：
> 先确定**哪个学科**（Scope）→ 再确定**具体主题**（Topic）→ 最后锁定**看哪本书**（Document）

### 3.2 第一级：Scope 排序 —— 锁定知识域

Scope 即「知识域」或「学科分类」，例如：HR 制度、产品手册、开发文档、运维手册。

**双路打分：**

| 打分方式 | 做法 |
|---------|------|
| **语义打分** | 用户问题和 Scope 描述文本都做 Embedding，算余弦相似度 |
| **词法打分** | 用 ES 做关键词匹配，捕捉语义模型可能漏掉的精确匹配信号 |

两分数**加权融合**后，取 **Top 5** 作为候选 Scope。

### 3.3 第二级：Topic 排序 —— 锁定主题

在候选 Scope 范围内细化到具体主题。例如 HR 制度下可能有：考勤与假期、薪酬福利、晋升制度。

**打分维度更丰富：**

| 维度 | 说明 |
|------|------|
| 语义打分 | 同 Scope 排序 |
| 词法打分 | 同 Scope 排序 |
| **关键词实体匹配** | 从问题提取关键词实体，和 Topic 路由文本匹配 |
| **Scope 归属加分** | Topic 属于排名第一的 Scope → **额外 +8 分** |

取 **Top 8** 作为候选 Topic。

### 3.4 第三级：Document 排序 —— 锁定文档

在候选 Topic 关联的文档范围内找最匹配的文档。**这一级打分最复杂，综合多个信号：**

| 打分维度 | 说明 | 权重 |
|---------|------|------|
| 语义相似度 | 问题与文档 Profile 的 Embedding 相似度 | **主分** |
| 词法匹配 | ES 关键词匹配分数 | 辅助分 |
| 关键词实体 | 问题关键词与文档路由文本的匹配度 | 辅助分 |
| **Scope 匹配加分** | 文档所属 Scope 与 Top Scope 一致 | **+15** |
| **Topic 关联加分** | 文档与候选 Topic 的关联强度 | **×20** |

> **为什么 Topic-Document 关联分数要 ×20 这么大的权重？**
> 因为 Topic 和 Document 之间的关联是在**知识库构建阶段就预先计算好的，质量很高**。
> 如果一份文档和某个 Topic 强关联，而这个 Topic 又是用户问题的最佳匹配，那这份文档大概率就是正确答案。
> **这个加分相当于把「领域专家的判断」注入到了路由决策中。**

### 3.5 置信度评估

排序完成后，系统**不是无脑取第一名**，还要评估结果可信度：

```
confidence = topScore / max(10, topScore + secondScore + 5)
```

**含义**：第一名分数占总分比例越高，置信度越高。如果第一名和第二名分数接近，说明系统也拿不准，置信度就低。

| 状态 | 条件 | 含义 |
|------|------|------|
| **SUCCESS** | 置信度 ≥ **0.55** | 系统很确定应该去这份文档找答案 |
| **LOW_CONFIDENCE** | 0 < 置信度 < 0.55 | 不太确定，仍用排名最高文档，但标记为低置信度 |
| **FAILED** | 无候选 | 完全找不到匹配文档 |

> **为什么不直接设一个分数阈值，低于就不路由？**
> 因为分数的**绝对值受很多因素影响**（Embedding 模型、文档数量、文本长度），不同知识库之间**没有可比性**。
> 而置信度看的是**相对差距**——第一名比第二名领先多少，这个指标**更稳定、更有实际意义**。

## 4. 影子路由：不打扰用户的质量观测

### 4.1 为什么要做

> 知识路由做好了，怎么知道它到底准不准？
> 最直接的办法是上线后看用户反馈，但**太被动了**。

### 4.2 核心思路

> **当用户手动选择了一份文档进行问答时，系统在后台悄悄跑一遍完整的知识路由算法**，看看系统自己会选哪份文档，然后和用户的实际选择做对比。

**整个过程对用户完全透明，不影响任何交互体验，所以叫「影子」路由。**

### 4.3 记录的信息

| 记录字段 | 说明 |
|---------|------|
| 原始问题 + 改写后问题 | 路由用的是改写后的问题，方便对比改写效果 |
| Top 3 Scope 候选 | 第一级排序前三名，含分数 |
| Top 3 Topic 候选 | 第二级排序前三名，含分数 |
| Top 3 Document 候选 | 第三级排序前三名，含分数 |
| 用户实际选择的文档 ID | 用户手动选的是哪份 |
| **是否命中** | 系统推荐第一名和用户选择是否一致（1/0） |
| 置信度 | 路由置信度分数 |
| 路由状态 | SUCCESS / LOW_CONFIDENCE / FAILED |

### 4.4 影子路由能回答的问题

| 问题 | 分析方法 |
|------|---------|
| 路由准确率是多少？ | 统计 `hitSelectedDocument = 1` 的比例 |
| 哪些场景路由容易出错？ | 筛选 `hitSelectedDocument = 0` 的记录，分析失败 case 共性 |
| 置信度阈值设得合不合理？ | 看 LOW_CONFIDENCE 状态下的实际命中率；若命中率不错，说明阈值可适当降低 |
| Scope / Topic 划分合不合理？ | 若某 Scope 下路由命中率明显低于其他，需调整知识域划分 |

> **本质**：这是一种**特殊的 A/B 测试**——
> A 组 = 用户真实选择（ground truth），B 组 = 系统自动路由结果。
> 通过持续对比两组数据，量化路由模型质量并有针对性优化。
>
> **这种「不打扰用户、持续收集反馈」的设计思路，在生产级 AI 系统中非常实用。**

## 5. 知识路由和检索链路怎么串起来

```
① DOCUMENT 模式（用户手动选了文档）
      → 直接用用户选的文档
      → 同时后台跑影子路由做质量观测

② AUTO_DOCUMENT 模式（系统自动选文档）
      → 走知识路由三级漏斗，自动锁定文档
      → 记录路由 Trace

③ 锁定文档后 → 进入 DocumentQuestionRouter
      → 根据问题类型决定走图查询还是混合检索

④ 最后执行检索和证据驱动生成
```

### 三者职责划分

```
知识路由     解决「去哪找」的问题
文档问题路由 解决「怎么找」的问题
检索引擎     解决「找什么」的问题
```

**三者各司其职，层层递进。**

## 6. 设计问答

### Q：你们的 RAG 系统是怎么处理多文档场景的？

> 我们设计了一套**知识路由机制**，在进入检索链路之前，先通过**三级漏斗（Scope → Topic → Document）**自动锁定最相关的文档。
> 每一级都用**语义 + 词法的混合打分**，最后通过**置信度评估**判断路由结果是否可靠。
> **置信度不够时会主动降级，不会硬猜。**

### Q：怎么评估路由效果？

> 我们做了**影子路由机制**。当用户手动选择文档时，系统在后台静默跑一遍完整路由，对比系统推荐和用户实际选择是否一致，把**命中率、置信度、候选排名**全部记录下来。
> 这样就能**持续量化路由质量**，有针对性地优化。

### Q：为什么用图数据库？

> 文档内部有天然的层级结构（章节、段落、条目），用户经常会问**结构性问题**，比如「第三章讲了什么」「上一节是什么」。这类问题**向量检索处理不了**，但图数据库天生擅长。
> 我们在 Neo4j 中构建了 **Document → Section → Item** 的结构图谱，支持章节定位、邻接遍历、子节点展开等图查询，**和向量检索形成互补**。
