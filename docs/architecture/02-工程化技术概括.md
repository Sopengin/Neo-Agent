# 03 - 工程化技术概括

---

## 1. 工程规范

| 规范 | 做法 |
|------|------|
| **分层架构** | business / common / framework 三层职责清晰，AI 业务逻辑、通用 Web 能力、基础设施组件互不耦合 |
| **统一异常处理** | 全局异常拦截 + 统一响应格式 `ApiResponse`，业务代码不需要到处 try-catch |
| **自动装配机制** | 基础组件通过 Spring Boot Starter 方式封装，引入依赖即可使用，零配置代码 |
| **MyBatis-Plus 自动填充** | 创建时间、更新时间等公共字段自动处理 |
| **API 文档规范** | Knife4j 增强的 Swagger，接口定义即文档 |

### 分层架构的模块职责

不是简单的 MVC 三层，而是按**领域职责**做了更细粒度拆分：

| 模块 | 职责 | 关键组件 |
|------|------|---------|
| `neo-agent-business-chat` | AI 对话业务 | Controller、执行器、编排器、检索服务 |
| `neo-agent-common-frame` | 框架层能力 | 统一响应、全局异常、自动填充 |
| `neo-agent-common-web` | Web 通用能力 | 请求拦截、跨域配置、参数校验 |
| `neo-agent-id-generator-framework` | 分布式 ID | 雪花算法、集群安全的 ID 生成 |
| `neo-agent-redisson-framework` | Redis 分布式 | 分布式锁、租约管理、延迟队列、重复执行限制 |

> **好处**：每一层可独立演进和复用。比如 Redis 分布式能力框架，不仅聊天场景用于会话锁定，文档处理场景同样可直接复用。

## 2. 集群安全与并发控制

> 这是很多开源项目完全忽略的部分，但在生产环境中至关重要。

一个 AI 对话系统如果不做并发控制，很容易出现：
- 同一条消息被**多个实例重复处理**
- 长对话**锁超时被其他实例抢占**

### 四个机制

| 机制 | 组件 | 作用 |
|------|------|------|
| **Redis 租约互斥** | `RedisLeaseManager` | 集群级别会话锁定，防止同一条消息被多实例重复处理 |
| **JVM 级任务注册** | `ChatRuntimeRegistry` | 维护进程内任务注册表，防止同进程重入 |
| **租约续期** | `BusinessChatService.startLeaseRenewal()` | 执行过程中自动续期，防止长对话超时导致锁释放后被抢占 |
| **优雅降级** | `BusinessChatService.cleanup()` | 无论成功失败都统一触发清理，**不留孤儿锁** |

### 为什么必须两层锁

```
只用 Redis 分布式锁 → 能防跨实例重复，但不能防同一 JVM 内的并发重入
只用 JVM 级锁       → 能防进程内重入，但不能防集群间重复

两层配合 → 分布式环境下才能做到万无一失
```

### 并发控制的完整生命周期

```
① 请求进入  → 在 ChatRuntimeRegistry 注册 JVM 级任务（防同进程重入）
② 获取租约  → 通过 RedisLeaseManager 获取集群级租约（防跨实例重复）
③ 自动续期  → 对话执行过程中后台线程自动续期（防长对话超时）
④ 执行完毕  → 主动释放 Redis 租约 + 注销 JVM 任务注册
⑤ 异常保护  → 任何环节异常，finally 块统一清理，不留孤儿锁
```

> 这套机制确保多实例部署下，每条消息**只被一个实例处理一次**，即使实例宕机或重启也不会出现数据不一致。

### 关键参数

| 参数 | 值 |
|------|-----|
| 租约 TTL | 30 秒 |
| 续期间隔 | 10 秒 |
| 锁键 | `chat:running:{conversationId}` |

## 3. 设计模式实战

> 不是为了用模式而用，每个都解决了实际的扩展性或解耦问题。

| 设计模式 | 应用场景 | 解决的问题 |
|---------|---------|-----------|
| **策略模式** | 三种会话记忆策略、四种切块策略 | 不同策略可插拔替换，新增策略不改已有代码 |
| **工厂模式** | 检索通道创建、切块器创建 | 复杂对象的创建逻辑集中管理 |
| **模板方法** | 文档处理流水线各节点 | 统一执行流程，子类只关注核心逻辑 |
| **责任链模式** | RAG 前置编排器的五步决策链 | 多个处理步骤按顺序串联，灵活组合 |
| **观察者模式** | SSE 流式输出回调 | 流式事件的异步通知与推送 |
| **AOP** | 重复执行限制、全局异常拦截 | 横切关注点与业务代码解耦 |

### 3.1 策略模式（会话记忆）

定义统一策略接口，三种实现（无记忆、滑动窗口、摘要压缩）各自独立。
系统通过**配置项**决定使用哪种，运行时通过**工厂方法**获取实现。

> 未来新增一种记忆策略（如基于 RAG 的长期记忆），只需新增实现类，**不修改任何已有代码**——开闭原则的实际落地。

### 3.2 责任链模式（前置编排器）

五步决策链：
```
路由判定 → 问题改写 → 歧义检测 → 子问题拆分 → 知识域收缩
```
每一步是一个独立处理节点，节点间链式调用。这种设计使得：

- 每个节点可独立开发和测试
- 可灵活调整节点执行顺序
- 可按需跳过某些节点（如简单问题不需要子问题拆分）
- 新增决策步骤只需加一个节点，不影响已有流程

### 3.3 模板方法（文档处理）

流水线每个阶段（解析、策略推荐、切块、向量化、索引构建）都遵循统一模板：

```
前置检查 → 核心逻辑 → 状态更新 → 日志记录
```

子类只需实现**核心逻辑**部分，其他环节由模板统一处理，确保整个流水线的**一致性和可追踪性**。

## 4. 可扩展性

> 核心模块都预留了扩展点，这是**企业级项目和 Demo 项目最本质的区别**。

| 扩展点 | 接口 / 协议 | 扩展方式 | 生效方式 |
|-------|-----------|---------|---------|
| 检索通道 | 检索通道接口 | 新增 Spring Bean | 自动参与检索 |
| 切块策略 | 切块策略接口 | 新增实现类 | 加入组合流水线 |
| 记忆策略 | 记忆策略接口 | 新增实现类 | 配置切换 |
| Agent 工具 | Tool 注册 | 注册新 Tool | 自动参与工具选择 |
| MCP 工具 | MCP 协议 | 部署 MCP Server | Agent 自动发现 |
| Skills 能力 | `SKILL.md` | 放入目录 | 零配置生效 |

> **不需要改框架代码，加个实现类或配置文件就完事了。**

### 依赖倒置原则

可扩展性不是「留了几个接口」这么简单，而是**贯穿整个系统的依赖倒置**——核心逻辑依赖抽象而非具体实现：

```
检索引擎不关心具体有几个通道、每个通道怎么实现 → 只关心「通道接口」
切块引擎不关心具体有几种策略                    → 只关心「策略接口」
```

> 这种设计使系统能**在不修改核心代码的前提下持续扩展新能力**。

## 5. 全链路可观测

基于 **AOP** 的全链路追踪，每个环节的耗时、输入输出、决策结果都有记录。

### 观测维度

| 观测维度 | 记录内容 | 用途 |
|---------|---------|------|
| **编排决策** | 路由结果、改写前后对比、子问题列表 | 分析编排逻辑是否合理 |
| **检索过程** | 各通道命中数、分数分布、融合结果 | 优化检索参数 |
| **证据评估** | 证据数量、质量评分、预算使用情况 | 调整证据阈值 |
| **模型调用** | 输入/输出 Token 数、响应延迟 | 成本分析和性能优化 |
| **工具调用** | 调用次数、成功率、平均耗时 | 工具可靠性监控 |
| **端到端延迟** | 各阶段耗时、总延迟 | 性能瓶颈定位 |

### 实际价值

> 用户反馈「回答不准确」或「响应太慢」时，传统做法是翻日志、加断点、猜测。
> 有全链路追踪后，直接打开观测面板看到完整链路：编排器走了哪个分支、检索了哪些文档、证据评分多少、模型用了多少 Token。
> **问题根因一目了然，大幅缩短排查时间。**

## 6. 与其他普通 Agent 项目的对比

| 对比维度 | 普通 RAG 项目 | Neo Agent |
|---------|--------------|-------------|
| 检索方式 | 单路向量检索 | 双通道并行（PGVector + ES）+ RRF 融合 + 可选 Rerank |
| 问题处理 | 原始问题直接检索 | 改写 + 子问题拆分 + 知识域收缩 |
| 意图判断 | 无 | 前置编排器五步决策 + 歧义主动追问 |
| 执行策略 | 所有问题走同一个模型 | 三层执行器按场景分流 |
| 会话记忆 | 全量塞给模型或不带 | 三种策略（无记忆/滑动窗口/摘要压缩） |
| 文档切块 | 固定长度一刀切 | 四种策略组合流水线 + 系统自动推荐 |
| 文档入库 | 同步处理，无日志 | Kafka 异步流水线 + 分步骤任务日志 |
| Agent 能力 | 无或仅简单对话 | ReAct 循环 + 联网搜索 + 工具调用 + Checkpoint 持久化 |
| 证据控制 | 无 | 预算裁剪 + 无证据短路防幻觉 |
| 检索粒度 | 命中什么用什么 | Parent-Child 块聚合 |
| 流式输出 | 简单 SSE 推文本 | 正文 + 引用来源 + 推荐追问 + 停止生成 |
| Agent 安全 | 无限制 | 模型/工具调用次数 Hook + 重试兜底 |
| MCP 协议 | 无或硬编码 Function Call | MCP 标准协议 + 动态发现 + 多工具编排 + 安全沙箱 |
| 能力扩展 | 固定能力，改代码才能加 | Skills 声明式定义 + 自动加载 + 热插拔 |
| 集群安全 | 单机运行 | Redis 租约互斥 + JVM 任务注册 + 租约续期 |
| 可观测性 | 无 | 全链路 Trace + 可视化观测面板 |
| 知识路由 | 无，全库检索 | 三级漏斗（Scope → Topic → Document） |
| 文档结构 | 无 | Neo4j 构建 Document → Section → Item 层级图谱 |
| 路由质量观测 | 无 | 影子路由静默对比 + 命中率追踪 |

## 7. 技术选型背后的考量

### 7.1 为什么用 PGVector + Elasticsearch 双引擎？

```
向量数据库  → 擅长语义理解，但对精确匹配弱
倒排索引    → 擅长精确匹配，但缺乏语义理解能力
两者互补才能覆盖用户检索的所有场景
```

- **PGVector**：与 PostgreSQL 深度集成，既是关系型数据库又支持向量检索，**运维成本低**
- **Elasticsearch**：倒排索引领域的**工业标准**，性能和功能久经验证

### 7.2 为什么用 Kafka 做异步解耦？

文档处理是典型**长耗时任务**（解析 → 切块 → 向量化 → 索引），同步处理用户要等很久。

- 用 Kafka 异步解耦后，**上传操作秒级完成**，后续处理后台异步进行
- Kafka 提供**可靠的消息投递保证**，即使处理实例宕机也不会丢失任务

### 7.3 为什么选 Spring AI 而不是 LangChain4j？

- Spring AI 是 **Spring 官方出品**，与 Spring Boot 生态深度集成
- 自动配置、依赖注入等 Spring 开发者熟悉的能力可无缝使用，**学习曲线最平滑**
- Spring AI Alibaba 在此基础上提供阿里云 DashScope 适配和 **ReactAgent** 实现

### 7.4 为什么选 Redisson 做分布式能力？

- 不仅有分布式锁，还有完善的**租约（Lease）机制、看门狗（Watchdog）自动续期、可重入锁**等高级特性
- 相比直接用 Redis 命令手写分布式锁，Redisson **更安全、更稳定、经过大量生产验证**

## 8. 总结

工程化水平体现在方方面面：

```
分层架构的模块解耦  →  集群环境下的并发安全
设计模式的恰当运用  →  全链路可观测的调试能力
面向接口的扩展性    →  每个技术选型背后的工程权衡
```

> 架构设计、并发控制、设计模式、技术选型 —— 项目在每一层都做了明确的工程权衡，
> 而不是把功能堆在一起。**这才是「企业级」三个字真正的含义。**
